IMDB — proving the domain layer earns its keep

Most of my day job is CRUD over an existing schema. IMDB was the project where I wanted a domain complex enough that Clean Architecture and DDD were the right tool, not decoration — a catalog where "what's a valid movie" is actually a rule, not just a database constraint.

View code on GitHub →

ARCHITECTURE

Web APIASP.NET Identity, JWT, role-based endpoints
→
Application45 MediatR commands & queries (CQRS)
→
DomainMovie/Series aggregates, value objects, invariants
→
InfrastructureEF Core migrations → SQL Server

DECISIONS

CQRS over one service per controllerSplitting reads and writes into MediatR handlers kept 45 operations organized as the API grew, instead of a handful of bloated services.
Invariants on the aggregate, not the APIValidation lives inside the entities, so an illegal state is impossible to construct — not just rejected at the edge by a filter.
Tests aimed at behaviour, not endpointsxUnit tests exercise domain rules and handlers directly, so a broken invariant fails fast without spinning up the whole API to notice.

THE PATTERN

A simplified version of the invariant-enforcing entities used across IMDB's aggregates:

public sealed class Movie : AggregateRoot
{
    private readonly List<CastMember> _cast = new();

    public static Result<Movie> Create(
        string title, DateOnly releaseDate, Rating rating)
    {
        if (releaseDate > DateOnly.FromDateTime(DateTime.UtcNow))
            return Result<Movie>.Fail(
                "Release date cannot be in the future.");

        return Result<Movie>.Ok(new Movie(title, releaseDate, rating));
    }

    public void AddCastMember(CastMember member)
    {
        if (_cast.Any(c => c.PersonId == member.PersonId))
            throw new DomainException(
                "This person is already cast in the movie.");

        _cast.Add(member);
        RaiseDomainEvent(new CastMemberAddedEvent(Id, member.PersonId));
    }
}

AdderHub — one codebase, two front doors

A social app usually needs a website and an API. AdderHub serves both — server-rendered pages for the site, a JWT-secured DRF API for anything else — from the same models and the same business logic, instead of maintaining two parallel implementations of "what's in my feed."

View code on GitHub →

ARCHITECTURE

Server-rendered viewsDjango templates, sessions
DRF APIJWT auth, Swagger/ReDoc
↓  both call the same service layer  ↓
ServicesFeed, posts, follows — one place decides the rules
↓
DataDjango ORM → database, Redis in front of the feed query

DECISIONS

One codebase, two front doorsThe website and the API call the same service functions, so a rule about the feed only has to be right once.
Redis in front of the feed, not the whole appThe following/explore feed is the most repeated read by far, so it's the one thing cached — not a blanket cache over everything.
UUID keys on public-facing modelsPost and profile IDs don't leak how many users or posts exist, without touching anything else in the schema.

THE PATTERN

A simplified version of the shared service layer behind both front doors:

class FeedService:
    """Shared by the server-rendered view and the DRF
    endpoint -- one place decides what's in a feed."""

    def __init__(self, cache):
        self.cache = cache

    def get_following_feed(self, user, page=1):
        key = f"feed:{user.id}:{page}"
        if cached := self.cache.get(key):
            return cached

        posts = (
            Post.objects
            .filter(author__in=user.following.all())
            .select_related("author")
            .prefetch_related("likes", "comments")
            .order_by("-created_at")
        )
        page_obj = paginate(posts, page)
        self.cache.set(key, page_obj, timeout=60)
        return page_obj
